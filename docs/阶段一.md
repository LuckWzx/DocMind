# 阶段一：知识库核心能力

> 目标：建成知识库的完整链路 — 文档导入 → 解析 → 分块 → 索引 → 检索 → 问答。
> 两人都是新手，借本项目学习 eino 框架，任务量需尽量对等。

---

## 分派原则

- **甲侧重"数据流水线"**：文档从上传到可被检索的全过程（数据层 + 模型层 + 解析层）
- **乙侧重"检索与对话"**：用户从提问到拿到答案的全过程（存储层 + 知识库 + 检索 + 对话）
- 各自的 Handler 和路由各自写，不设独立模块
- 先定义接口再编码，弱化依赖阻塞

---

## 甲 负责领域 —— 数据流水线

### 模块1：数据持久层

**目标**：定义所有表结构和领域模型，实现 Repository。

| 子任务 | 说明 |
|---|---|
| PostgreSQL 连接 + 迁移 | 连接池配置、GORM AutoMigrate 建表 |
| 领域模型定义 | Tenant、User、KnowledgeBase、Knowledge、Chunk、Session、Message、FAQ、Tag |
| Repository 接口定义 | 在 `types/interfaces/` 下定义各实体仓储接口 |
| Repository 实现 | GORM 实现 CRUD + 分页 + 条件查询 + 批量插入 |

**交付标准**：所有表自动建表，每个 Repository 单测 CRUD 通过。

---

### 模块2：模型适配层

**目标**：统一封装 Chat / Embedding / Rerank 三种模型能力。这是乙的上游依赖，优先交付接口。

> VLM、ASR 不纳入阶段一，接口预留即可。

| 子任务 | 说明 |
|---|---|
| Provider 注册机制 | 配置文件声明模型供应商，Provider 解析 endpoint / API Key |
| Chat 接口 + 实现 | 对话补全（含流式 channel），OpenAI 兼容协议，eino 的 ChatModel 封装 |
| Embedding 接口 + 实现 | 文本向量化，返回 `[]float64`，OpenAI 兼容协议 |
| Rerank 接口 + 实现 | 候选列表重排序，返回打分列表 |

**交付标准**：接口交付后，乙能拿到 `Chat`/`Embedding`/`Rerank` 三个 interface 做开发，先用 mock 跑通，甲后面补齐 OpenAI 实现。

---

### 模块3：基础设施层

**目标**：文本分块 + 文档解析（gRPC 对接 Python docreader）。

| 子任务 | 说明 |
|---|---|
| chunker | 按分隔符递归拆分（段落→句子），chunk_size / chunk_overlap 可配置 |
| docreader gRPC Client | Go 侧 Client 封装，连接 docreader Python 服务 |
| docreader Python 服务 | PDF / Word / Markdown / TXT / HTML → 输出 Markdown + 图片引用列表 |
| web_search 基础 | DuckDuckGo 关键词搜索，返回 Top-N |

**交付标准**：上传 PDF → docreader 解析为 Markdown → chunker 分块为 Chunk 列表 → 可以交给乙入库。

> Excel / PPT / 图片 OCR 在阶段二补齐。

---

### 模块4：文件服务

**目标**：文件上传下载的基础能力。

| 子任务 | 说明 |
|---|---|
| FileStorage 接口 | Upload / Download / Delete |
| 本地存储实现 | 阶段一默认存本地文件系统 |
| MinIO 实现 | 备选，接口一致可切换 |

**交付标准**：文件可上传到指定目录，可通过 API 下载。

---

## 乙 负责领域 —— 检索与对话

### 模块5：向量存储

**目标**：抽象向量存储层，让知识库的 chunk 能存能搜。

| 子任务 | 说明 |
|---|---|
| VectorStore 接口 | Insert / Delete / Search（相似度 + 过滤条件 + TopK） |
| pgvector 实现 | PostgreSQL 原生向量扩展，阶段一默认方案 |
|                  |                                                      |

**交付标准**：甲传来的 embedding 向量能存入，能按相似度搜出 Top-K。

---

### 模块6：知识库管理

**目标**：知识库 CRUD + 知识条目全生命周期管理。

| 子任务 | 说明 |
|---|---|
| 知识库 CRUD | 创建/编辑/删除，配置分块参数、模型选择 |
| 知识条目全流程 | 收到甲的解析结果 → 调甲的 Embedding → 写入自己管的 VectorStore |
| 条目状态机 | pending → parsing → indexing → completed / failed |
| FAQ 管理 | FAQ 问答对增删改查 + 批量导入 |
| Tag 标签 | 标签分类与筛选 |
| 级联删除 | 删知识库时清理 chunk、向量、FAQ |

**交付标准**：Web 端上传文档 → 后台自动解析 → 索引 → 条目状态"已完成"。

---

### 模块7：检索与后处理

**目标**：用户输入问题，返回相关文档片段。

| 子任务 | 说明 |
|---|---|
| 向量检索 | 调用 VectorStore.Search() 返回 Top-K |
| 关键词检索 | BM25 倒排索引，返回 Top-K |
| RRF 融合 | 两路结果用 RRF 算法合为一路 |
| Rerank 重排序 | 调甲的 Rerank 接口对融合结果精排 |
| TopK 截断 + 合并 | 相邻 chunk 合并、去重、overlap 处理 |

**交付标准**：输入 query → Top-5 排序 chunk 列表，含来源和分数。

---

### 模块8：会话与对话管道（经典 RAG）

> 注意：阶段一是**单步 RAG**，不是 Agent。没有工具调用、没有多步推理、没有 ReAct 循环。
> Agent 编排是阶段二才做的事。

**RAG 流程（阶段一）**：

```
用户提问 → 检索知识库 → 获得 Top-K chunk → 拼入 Prompt → LLM 生成 → 流式返回
          ═══════════════ 一步完成，固定路线 ═══════════════
```

**Agent 流程（阶段二，对比）**：

```
用户提问 → LLM 思考 → 决定调什么工具 → 观察结果 → 再思考 → 可能再调工具 → ... → 最终回答
          ═══════════════ 多步循环，LLM 自主决策 ═══════════════
```

**目标**：用户创建会话、提问，系统检索知识库后由 LLM 生成答案并流式返回。

| 子任务 | 说明 |
|---|---|
| Session 管理 | 创建/删除/列表/历史消息加载 |
| Chat Pipeline 框架 | 固定插件链：search → rerank → merge → into_chat_message → chat_completion |
| SSE 流式响应 | 调甲的 Chat 流式接口 → SSE 推送给前端 |
| 基础 Prompt 模板 | 知识问答 system prompt + 检索结果注入 |

**交付标准**：创建会话 → 提问 → 检索 + LLM 流式返回 → 前端逐字显示。

## 阶段二预览

阶段一完成后，两人在稳定的知识库底座上进入 Agent 开发。核心变化：

```
阶段一的 RAG                      阶段二的 Agent
─────────────                    ────────────────
用户提问                         用户提问
  ↓                                ↓
固定检索（模块7）                  LLM 自主决定"要不要检索"
  ↓                                ↓
固定拼 Prompt（模块8）             动态选择工具（检索/搜索/计算/...）
  ↓                                ↓
LLM 一次生成答案                  多步 ReAct 循环直到最终答案

模块8 的 Pipeline → 升级为 → Agent 的 ReAct 循环
模块7 的检索   → 包装为   → Agent 的知识库检索工具
模块2 的 Chat   → 复用为   → Agent 的决策大脑
```
