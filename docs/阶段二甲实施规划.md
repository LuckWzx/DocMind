**目标**：对话过长时自动压缩旧消息为摘要，保证 Agent 与 RAG 都不丢上下文、Token 不超限。

**交付标准**：

#### 3.2.2 quick-answer 模式 → 自研 Consolidator（参考 WeKnora）✅ 已实现

> 2026-08-07 落地：`consolidator.go`（压缩器）+ 复用 `raw_archive.go` / `pkg/token`，已接入 `chat_service.go`（KnowledgeChat 加载历史后、构建 pipeline.Context 前，对应 [chat_service.go:160](file:///f:/github_code/DocMind/internal/service/chat_service.go#L160)）；单测 6 个场景通过。摘要模型懒创建 + 缓存（复用 `agentConfig.ModelID`），压缩失败仅记日志不阻断对话。

> **2026-08-07 增量压缩升级**：新增 `session_summaries` 表（`entity.SessionSummary`，AutoMigrate 注册）+ `SummaryRepository`（GetBySession / Upsert / DeleteBySession）；`ConsolidateIncremental(ctx, oldSummary, incremental)` 只把"旧摘要 + 边界后增量消息"送 LLM 合并，压缩成本与历史总长无关；`chat_service` 加载逻辑改为"读摘要 → 增量加载（`ListAfterID`）→ 合并 → Upsert 写回（LastMessageID 边界）"。降级保留旧摘要 + 归档增量。删除/清空会话联动清理摘要。Agent 模式（官方中间件 state 常驻）天然增量，无需改造。

> **2026-08-07 触发缺陷修复 + HistoryTurns 语义重定义**：原实现"无摘要时只加载最近 N 轮（HistoryTurns×2）"导致 Token 永远达不到压缩阈值（80k）、首份摘要永不产生——滑动窗口掐死压缩触发（WeKnora 无此问题：其 Agent 模式全量加载+压缩、普通问答仅窗口丢弃，两者不同时使用）。修复：无摘要时**全量加载**（上限 500 条），Token 自然累积触发。**HistoryTurns 重定义为"压缩时保底保留的最近完整轮数"**：对话过长触发压缩时，最近 N 轮以原文保留不压缩（与摘要一起发给模型），更早历史才被压缩；`Consolidator` 新增 `preserveTurns`（默认 5，与 Agent 模式 `PreserveTurns` 语义统一），窗口校验（保底轮数+当前轮+摘要预留 ≤ maxTokens）保证不撑爆窗口；`BuildAgentContext` 的 `historyTurns` 参数维持废弃（签名保留兼容）。

- pipeline 是 `compose.Graph`，历史消息在 `chat_service.go` 加载后经 `node_build_prompt` 拼入
- 在 `chat_service.go` 加载 history 之后、构建 `pipeline.Context` 之前插入压缩（对应 [chat_service.go:118-154](file:///f:/github_code/DocMind/internal/service/chat_service.go#L118-L154)）

type Consolidator struct {
    model      model.BaseModel[*schema.Message] // 摘要模型（复用 ChatModelFactory）
    estimator  *token.Estimator                  // pkg/token，tiktoken-go cl100k_base

**压缩规则**（与阶段二.md 一致）：
- 保留：system prompt（首条）+ 当前轮（最后 user 及之后全部）+ 预算内近 N 条历史
- 压缩：其余历史 → 单条 `[Memory Summary - N earlier messages consolidated]` system 消息
- **tool_call 边界保护**：从历史尾部回扫时按"tool 组 + 前驱 assistant"整体保留（参考 WeKnora `findKeepBoundary`），杜绝半截配对
- **降级**：LLM 摘要失败 3 次（60s 超时）→ `rawArchive` 原文归档

#### 4.2.2 图模型与 MemoryRepository（参考 WeKnora `memory/neo4j/repository.go`）

```
(Episode {id, user_id, session_id, summary, created_at})
    -[:MENTIONS]-> (Entity {name, type, description})

```

```go

```

- 写入：`MERGE (e:Episode {id})` + `MERGE (n:Entity {name, user_id})` + `MERGE (e)-[:MENTIONS]->(n)` + `MERGE (s)-[r:RELATED_TO]->(t)`（单事务完成）
- 检索：`MATCH (e:Episode)-[:MENTIONS]->(n:Entity) WHERE e.user_id=$uid AND n.name IN $keywords RETURN DISTINCT e ORDER BY e.created_at DESC LIMIT $limit`

#### 4.2.3 记忆提取（对话结束后 LLM 结构化提取）

## 六、模块4：Python 沙箱（Docker，Week 4-5）

### 6.1 目标与交付标准

**目标**：为数据计算工具提供隔离的 Python 代码执行环境。

**交付标准**：Agent 说"分析表格季度趋势" → 检索数据 → 沙箱执行 Python → 返回分析结果（文本/DataFrame/图表）。

> ✅ 2026-08-07 决策：采用 **Docker 容器**方案（参考 WeKnora `sandbox/docker.go` + `manager.go`），隔离性优于本地进程；开发机需 Docker。

### 6.2 设计要点

#### 6.2.1 架构（参考 WeKnora sandbox 包）

```go
// internal/sandbox/interface.go — 交付乙的核心接口
type Sandbox interface {
    Execute(ctx context.Context, req *ExecuteRequest) (*ExecuteResult, error)
    IsAvailable(ctx context.Context) bool
}
type ExecuteRequest struct {
    Code     string        // Python 代码
    Timeout  time.Duration // 默认 30s
}
type ExecuteResult struct {
    OK       bool            // 执行是否成功
    Text     string          // 文本输出（print 结果）
    Data     interface{}     // DataFrame → JSON（序列化结构）
    Image    string          // 图表 → base64 PNG
    Error    string          // 错误信息（截断）
    Duration time.Duration
}
```

- **Manager 层**（`manager.go`）：沙箱类型选择（`docker` / `disabled`，配置 `sandbox.type`）+ 可用性探测 + 镜像预拉取（`EnsureImage` 异步）+ 执行前 `ScriptValidator` 静态安全校验（即使容器隔离也做第一道防线，防 prompt 注入类恶意代码）

#### 6.2.2 Docker 隔离参数（参考 WeKnora `docker.go buildDockerArgs`）

```
docker run --rm \
  --user 1000:1000 \                  # 非 root
  --cap-drop ALL \                    # 丢弃全部能力
  --read-only --tmpfs /tmp:rw,noexec,nosuid,size=64m \  # 只读根文件系统
  --memory 512m --memory-swap 512m \  # 内存限制（禁 swap）
  --cpus 1.0 \                        # CPU 限制
  --network none \                    # 无网络
  --pids-limit 100 \                  # 进程数限制
  --security-opt no-new-privileges \  # 禁止提权
  -v <script_dir>:/workspace:ro \     # 代码只读挂载
  sandbox-image python3 /workspace/main.py
```

- 超时：`context.WithTimeout` 包裹 `docker run`，超时 kill + `--rm` 自动清理容器
- 镜像：`python:3.11-slim` + `duckdb` + `pandas` + `matplotlib`（Dockerfile 放 `deploy/sandbox/`，构建一次缓存）

#### 6.2.3 执行协议

- 代码写入临时目录（`data/sandbox/`，每次执行唯一子目录）→ bind mount 进容器只读执行
- 约定：代码末尾自动追加结果序列化片段（`print` 捕获 + `json.dumps` 输出 DataFrame / matplotlib `savefig` 到 `/tmp` 再读出转 base64），执行结果从 stdout 结构化返回
- DuckDB：`data_analysis` 工具生成的 SQL 分析代码直接 `duckdb.connect()` 执行（数据文件同目录只读挂载）

#### 6.2.4 降级

- Docker 不可用 → `IsAvailable()=false`，`data_analysis` 工具返回"数据分析功能暂不可用"；不阻塞其他工具
- 沙箱镜像缺失 → 启动时自动 `docker pull`

### 6.3 实施步骤（Week 4-5）

1. **Day 1-2**：`internal/sandbox/` 接口 + DockerSandbox（docker run 参数组） + `cmd/sandboxdemo` 验证执行/超时/隔离
2. **Day 3-4**：ScriptValidator（黑名单：`open/os/subprocess/socket/requests/import 系统模块` 等）+ 安全测试（尝试逃逸 → 应被拒/隔离）
3. **Day 5-6**：DuckDB 集成（镜像构建 + SQL 分析验证）
4. **Day 7-8**：结果序列化（文本/DataFrame→JSON/图表→base64）
5. **Day 9**：`Sandbox` 接口交付乙 + `data_analysis` 工具接真沙箱（替换 mock）
