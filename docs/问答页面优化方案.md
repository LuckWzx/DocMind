# 问答页面优化方案

> 针对 Agent 问答过程中**状态展示、思考过程、工具调用**的实时呈现进行整体优化，提升用户对 Agent 执行过程的可感知性与可控性。

## 一、背景与目标

### 1.1 现状

当前系统已实现 Agent 执行过程的实时上报：

- **后端**：Eino ADK 引擎 → `internal/agent/runner.go` 展开为统一事件 → chat controller 通过 SSE 逐条推送
- **事件类型**：`state`（状态机）、`agent_step`（工具步骤）、`answer`（回答增量）、`error`、`complete`
- **状态机**：`init → thinking → searching → generating → completed / cancelled / failed`
- **前端**：`useChatStreamHandler.ts` 接收 SSE 事件 → `AgentStreamDisplay.vue` 渲染思考卡片、工具调用卡片

### 1.2 存在问题

| 问题 | 影响 |
|------|------|
| 状态事件仅含状态名，无上下文详情 | 用户只能看到"思考中/搜索中"，不知道在搜什么 |
| 思考内容仅在完成后可查看，无实时流式展示 | 用户等待时缺乏过程反馈 |
| 工具调用展示样式统一，缺少差异化 | 检索类/代码类/网络类工具难以一眼区分 |
| 工具执行中无进度反馈（长耗时工具"卡住"假象） | 用户误以为系统无响应 |
| 大量事件（尤其 answer 增量）逐个渲染，性能开销大 | 长回答时页面卡顿 |
| 用户无法中途干预（取消当前工具、手动确认） | 执行失控，只能等流结束 |
| 调试信息分散，问题排查困难 | 前后端联调成本高 |

### 1.3 优化目标

1. **可感知**：Agent 每一步执行都有清晰的视觉反馈与文案说明
2. **可理解**：思考过程、工具输入输出以结构化、可折叠的方式呈现
3. **可控**：用户可取消/确认关键操作
4. **高性能**：事件量增大时渲染依旧流畅
5. **可调试**：支持完整事件流与耗时指标的查看与导出

## 二、当前架构梳理

### 2.1 后端事件链路

```
Eino ADK AsyncIterator[*adk.AgentEvent]
        │
        ▼
internal/agent/runner.go  EventStream.expand()
        │  (状态机转换 + 步骤记录 + 事件展开)
        ▼
统一事件 OutputEvent (state / agent_step / answer / error / complete)
        │
        ▼
internal/api/v1/chat/controller.go  AgentChat()
        │  (emitAgentEvent 映射为 SSE 事件)
        ▼
前端 SSE 流 (response_type: state / agent_step / answer / ...)
```

### 2.2 前端事件链路

```
fetchEventSource (web/src/api/chat/streame.ts)
        │
        ▼
useChatStreamHandler.ts  onmessage 分发
        │  (agentEventStream 事件数组 + _eventMap 去重)
        ▼
AgentStreamDisplay.vue 渲染
        │  (thinking 卡片 / tool_call 卡片 / 折叠树)
        ▼
tool-results/*.vue 工具结果差异化渲染
```

### 2.3 关键代码位置

| 模块 | 文件 | 职责 |
|------|------|------|
| 后端事件展开 | `internal/agent/runner.go` | ADK 事件 → 统一事件 |
| 后端状态机 | `internal/agent/state.go` | 状态转换与合法性校验 |
| 后端事件类型 | `internal/agent/types.go` | OutputEvent 定义 |
| 后端 SSE 映射 | `internal/api/v1/chat/controller.go` | emitAgentEvent 转发 |
| 前端事件处理 | `web/src/composables/useChatStreamHandler.ts` | SSE 分发与消息维护 |
| 前端展示 | `web/src/views/chat/components/AgentStreamDisplay.vue` | Agent 过程渲染 |
| 前端工具结果 | `web/src/views/chat/components/tool-results/` | 各工具结果渲染器 |

## 三、优化方案

### 3.1 后端：状态事件增强（高优先级）

#### 3.1.1 状态事件携带上下文详情

**现状**：`state` 事件只推送 `thinking/searching/generating` 等状态名，前端只能显示固定文案。

**方案**：为 `OutputEvent` 增加 `StateDetail` 字段，携带当前状态的具体动作描述。

```go
// internal/agent/types.go
type OutputEvent struct {
    Type        OutputEventType    `json:"response_type"`
    Content     string             `json:"content,omitempty"`
    State       string             `json:"state,omitempty"`
    // 新增：状态详情（如 "正在调用知识库检索工具 kb_search"）
    StateDetail string             `json:"state_detail,omitempty"`
    // 新增：进度信息（如 {current: 2, total: 3} 表示第 2/3 轮工具循环）
    Progress    *AgentProgress     `json:"progress,omitempty"`
    // ... 现有字段
}

type AgentProgress struct {
    Current int `json:"current"` // 当前轮次
    Total   int `json:"total"`   // 总轮次（0 表示未知）
}
```

**推送时机**（`internal/agent/runner.go`）：

- `thinking`：`"正在理解问题并规划执行步骤"`
- `searching`：`"正在执行工具 {tool_name}"`（携带工具名）
- `generating`：`"正在生成回答内容"`

#### 3.1.2 工具调用声明事件携带元数据

**现状**：`agent_step` 声明阶段仅含 `tool_name + tool_args`，前端无法预知工具类型。

**方案**：声明事件增加 `ToolMeta`（工具分组、展示类型），让前端无需硬编码工具名即可差异化渲染。

```go
type ToolMeta struct {
    Group       string `json:"group,omitempty"`        // search / code / web / mcp / data
    DisplayType string `json:"display_type,omitempty"` // 对应前端 ToolResultRenderer
    Icon        string `json:"icon,omitempty"`         // 建议图标名（前端可覆盖）
    Description string `json:"description,omitempty"`  // 工具用途简述
}
```

工具分组判定表：

| 分组 | 工具示例 | 展示特征 |
|------|----------|----------|
| search | kb_search、search_knowledge | 结果摘要、引用溯源 |
| web | web_search、web_fetch | 网页卡片、链接 |
| data | data_analysis、python_exec | 表格、图表、代码 |
| mcp | 外部 MCP 工具 | 服务标识、审批状态 |
| system | todo_write、thinking | 计划、思考卡片 |

#### 3.1.3 思考内容实时流式推送

**现状**：思考内容（reasoning）只在每轮完整结束后随 `agent_step` 或折叠进回答，无法实时展示。

**方案**：新增 `EventThink` 事件类型（`response_type: "think"`），在流式消费模型 chunk 时同步推送推理内容增量：

```go
// internal/agent/runner.go expandAssistant 流式分支
for {
    chunk, err := mv.MessageStream.Recv()
    // ...
    if chunk.Content != "" {
        s.ch <- &OutputEvent{Type: EventAnswer, Content: chunk.Content}
        s.cur.Thought += chunk.Content
    }
    // 新增：推理内容（若有 reasoning_content 字段）
    if reasoning := extractReasoning(chunk); reasoning != "" {
        s.ch <- &OutputEvent{Type: EventThink, Content: reasoning}
    }
}
```

> 注意：需确认底层 ChatModel 是否透出 reasoning_content（Qwen3 系列支持）；不支持时保持现状，由 thinking 卡片兜底。

### 3.2 前端：展示层优化（高优先级）

#### 3.2.1 状态栏增强

**现状**：`getAgentStateLabel()` 只映射固定状态文案。

**方案**：

```typescript
// AgentStreamDisplay.vue
const getAgentStateLabel = (state?: string, detail?: string): string => {
  if (detail) return detail
  switch (state) {
    case 'thinking': return t('chat.agentStateThinking')
    case 'searching': return t('chat.agentStateSearching')
    case 'generating': return t('chat.agentStateGenerating')
    case 'cancelled': return t('chat.agentStateCancelled')
    default: return t('chat.thinkingAlt')
  }
}
```

- 状态文案优先使用 `state_detail`，后端未推送时回退固定文案
- 状态标签附加动态指示器（旋转图标 / 波浪动画），区分"进行中"与"已完成"

#### 3.2.2 思考卡片实时刷新

- 收到 `think` 事件时，直接追加到当前 thinking 卡片内容（而非等待整轮结束）
- thinking 卡片默认折叠为摘要行，点击展开查看完整推理
- 折叠摘要：取思考内容前 N 个字符（如 60），末尾追加省略号

#### 3.2.3 工具卡片差异化

基于 `ToolMeta.group`（后端推送）或现有 `getToolIconName()` 映射（兜底）：

| 分组 | 视觉特征 |
|------|----------|
| search | 蓝色系图标 + 命中数量徽标 |
| web | 绿色系图标 + 域名徽标 |
| data | 紫色系图标 + 执行耗时徽标 |
| mcp | 橙色系图标 + 服务名徽标 |
| system | 灰色系图标 + 无结果样式 |

#### 3.2.4 工具执行进度反馈

- 工具调用声明（pending）后超过 **3 秒** 未返回结果：卡片显示"执行中..." + 脉冲动画
- 长耗时工具（data_analysis / python_exec）在结果回填时展示耗时徽标：`耗时 2.4s`
- 工具失败（`success: false`）：卡片红色边框 + 可展开错误详情

### 3.3 性能优化（中优先级）

#### 3.3.1 answer 增量批量渲染

**现状**：每个 `answer` chunk 触发一次 DOM 更新，长回答时渲染频繁。

**方案**：

- 前端对 answer 事件做 **16ms 帧合并**（requestAnimationFrame 节流）：

```typescript
// useChatStreamHandler.ts
let answerBuffer = ''
let rafId: number | null = null

const flushAnswer = () => {
  if (!answerBuffer) return
  appendContent(answerBuffer)
  answerBuffer = ''
  rafId = null
}

// onmessage 中
if (responseType === 'answer') {
  answerBuffer += content
  if (!rafId) rafId = requestAnimationFrame(flushAnswer)
}
```

- 消息文本区使用 `contenteditable` 或单 DOM 节点追加（避免整段 v-html 重渲染）

#### 3.3.2 事件流瘦身

- 后端心跳（`ping`）事件不含 `response_type`，前端已忽略，保持现状
- 工具结果超过 `maxResultLen`（500 字符）截断，前端无需处理大文本
- 可考虑：answer 事件合并为 `{content: "..."}` 纯文本负载，减少 JSON 解析开销

#### 3.3.3 长对话虚拟滚动

- 消息列表过长时（> 100 条），对历史消息做虚拟滚动
- Agent 事件流区（中间步骤树）节点较多时懒渲染：仅渲染可见节点 + 折叠节点只渲染摘要

### 3.4 交互优化（中优先级）

#### 3.4.1 用户停止增强

**现状**：停止后仅保存已生成内容，无过程状态提示。

**方案**：

- 停止时发送 `state: cancelled` 事件，前端将进行中的工具卡片标记为"已停止"
- 停止后展示"已停止生成"提示条，附带"重新生成"按钮（复用现有 regenerate 逻辑）

#### 3.4.2 工具调用手动确认（可选）

- 对高风险工具（python_exec、外部 MCP 写操作）支持 `tool_approval_required` 确认流（后端已有 `mcp_tool_approval` 实体支撑）
- 前端 ToolApprovalCard 已存在，扩展至普通工具（如 python_exec 首次执行确认）

### 3.5 调试能力（低优先级）

#### 3.5.1 事件流调试面板

- 开发模式（`import.meta.env.DEV`）下，消息右上角显示调试入口
- 面板展示：完整事件序列（时间线）、每个事件的原始 JSON、耗时统计（首 token / 工具平均耗时 / 总耗时）
- 支持一键复制事件 JSON 导出

#### 3.5.2 后端耗时指标

- `sseStats` 已有 open / first_token / event / close 统计，补充：
  - 每个 `agent_step` 的 `duration`（声明 → 结果回填）已存在，前端展示
  - 每轮 thinking → searching 的状态驻留时间（可用于定位慢工具）

## 五、验收标准

### 功能验收

- [ ] 提问后，状态栏实时展示 `思考中 → 执行工具 → 生成中` 全流程
- [ ] 思考内容实时流式出现在 thinking 卡片中，可折叠展开
- [ ] 不同工具类型（检索/网页/数据/代码）视觉可区分
- [ ] 工具执行超过 3 秒有"执行中"动画反馈
- [ ] 工具结果回填后展示耗时
- [ ] 用户停止后，进行中的卡片标记为"已停止"，可重新生成
- [ ] 历史消息回放（reconstructEventStreamFromSteps）与实时流展示效果一致

### 性能验收

- [ ] 500 字以上长回答无感知卡顿（帧率 ≥ 50fps）
- [ ] 单轮 10+ 工具调用的事件流渲染流畅
- [ ] 心跳事件不产生渲染开销

### 兼容性验收

- [ ] 快速问答（knowledge-chat）不受 Agent 事件改动影响
- [ ] 嵌入模式（embed）展示一致
- [ ] 断线重连后，已到达事件可恢复展示

## 六、风险与注意事项

| 风险 | 应对 |
|------|------|
| 底层模型不透出 reasoning_content | think 事件降级：不推送，thinking 卡片兜底 |
| 状态详情文案硬编码导致多语言缺失 | 详情文案走 i18n，后端只推结构化标识（如 tool_name） |
| 事件字段膨胀增加带宽 | 新增字段全部 `omitempty`，旧前端兼容 |
| 帧合并引入首字延迟 | 帧合并仅针对 answer 增量，首个 chunk 立即渲染 |
| 工具分组映射表维护成本 | 后端 ToolMeta 兜底 + 前端正则兜底，双保险 |
