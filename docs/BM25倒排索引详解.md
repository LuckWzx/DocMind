# BM25 倒排索引详解

> 本文用 DocMind 项目的真实场景，讲解"倒排索引"与"BM25 打分"的原理，并给出完整手算实例。

## 一、倒排索引（Inverted Index）

### 1.1 问题：电脑怎么"找"文档？

假设上传了 3 份文档，被切成 3 个 chunk：

| chunk | 内容 |
|---|---|
| 1 | 数据库连接配置教程：如何配置连接池 |
| 2 | Redis 缓存配置指南 |
| 3 | 数据库性能调优与索引优化 |

用户问 **"数据库配置"**，电脑需要在 3 个 chunk 里找包含这两个词的内容。

**正排扫描（笨办法）**：把 3 个 chunk 从头到尾读一遍，逐字比对。文档少没问题，但 10 万个 chunk 时每次提问都全表扫描，性能不可接受。

**倒排索引（聪明办法）**：像书的目录反过来——不记"第 1 页有什么"，而记"**某个词出现在哪些页**"。

### 1.2 建索引过程

先对每个 chunk 分词（jieba 切词），再建立"词 → 文档列表"的映射：

```
词条（term）      →   倒排表（postings）
─────────────────────────────────────────────
"数据库"          →   chunk1, chunk3
"配置"            →   chunk1, chunk2
"连接"            →   chunk1
"Redis"           →   chunk2
"性能"            →   chunk3
"优化"            →   chunk3
```

这就是**倒排索引**——"倒"是相对正排（文档→词）而言，方向是**词→文档**。

### 1.3 检索过程

查询时直接查表：

```
"数据库" → {1, 3}
"配置"   → {1, 2}
并集候选 → {1, 2, 3}
```

查表是 O(1) 级别的哈希查找，百万级文档也无压力。

### 1.4 在 DocMind 中的形态

项目数据库（PostgreSQL 17.9）已安装 **pg_search 0.22.2** 扩展（底层 Tantivy 引擎），对 `chunks` 表建 `USING bm25` 索引后，倒排表由数据库自动维护——chunk 增删改时自动同步，业务代码零改动。

## 二、BM25 打分算法

倒排索引只解决"哪些 chunk 沾边"，排序要靠 BM25 打分。

### 2.1 公式

每个查询词贡献值的累加：

\[
\text{score}(d, q) = \sum_{t \in q} \text{IDF}(t) \times \frac{tf(t,d) \times (k_1 + 1)}{tf(t,d) + k_1 \times (1 - b + b \times \frac{dl}{avgdl})}
\]

默认参数：\(k_1 = 1.5\)，\(b = 0.75\)。

### 2.2 公式背后的四个直觉

**直觉 1：词出现越多越相关（TF 词频）**

chunk 里"配置"出现 3 次比 1 次更相关，但收益递减——出现 3 次 ≠ 3 倍相关。分子分母都带 \(tf\)，贡献随次数增长越来越平缓，\(k_1=1.5\) 控制弯曲程度。

**直觉 2：越稀有的词越值钱（IDF 逆文档频率）**

\[
\text{IDF}(t) = \ln\left(1 + \frac{N - df(t) + 0.5}{df(t) + 0.5}\right)
\]

- \(N\) = 总 chunk 数，\(df(t)\) = 含词 \(t\) 的 chunk 数
- "配置"在 1000 个 chunk 都出现 → 无区分度，不值钱
- "PostgreSQL" 只有 2 个 chunk 有 → 一出现就高度相关，很值钱
- "的、了、怎么"这类词 IDF 趋近于 0，天然无意义

**直觉 3：短文档更可能是"刚好命中"（长度归一化）**

2000 字的 chunk 出现 1 次"配置"，和 50 字的 chunk 出现 1 次"配置"，后者含金量高（词密度大）。\(dl/avgdl\)（文档长度 ÷ 平均长度）实现这一点：文档越短分母越小、得分越高。\(b=0.75\) 表示长度惩罚强度（0 = 不管长度，1 = 完全按长度惩罚）。

**直觉 4：只比排名不比分数（量纲）**

BM25 分数是任意非负数，与向量检索的 cosine 分数（0~1）**完全不可比**——这是两路结果需要用 RRF（Reciprocal Rank Fusion，只比名次）融合的根本原因。

## 三、完整手算实例

### 3.1 数据

jieba 分词后各 chunk 词项数：

| chunk | 内容 | 词项数 dl |
|---|---|---|
| 1 | 数据库/连接/配置/教程：如何/配置/连接池 | 8 |
| 2 | Redis/缓存/配置/指南 | 5 |
| 3 | 数据库/性能/调优/与/索引/优化 | 6 |

平均长度 \(avgdl = (8+5+6)/3 \approx 6.33\)，总文档数 \(N=3\)。

query：**"数据库 配置"**（两个词：数据库、配置）

### 3.2 第 1 步：算 IDF

- "数据库" 出现在 chunk1、chunk3 → \(df=2\)
- "配置" 出现在 chunk1、chunk2 → \(df=2\)

\[
\text{IDF(数据库)} = \ln\left(1 + \frac{3-2+0.5}{2+0.5}\right) = \ln(1.6) \approx 0.47
\]

"配置"同理 ≈ 0.47。

### 3.3 第 2 步：算每个 chunk 的 TF 部分（各词出现 1 次，\(k_1=1.5, b=0.75\)）

**chunk1**（dl=8，命中"数据库"+"配置"）：

\[
\frac{1 \times 2.5}{1 + 1.5 \times (0.25 + 0.75 \times \frac{8}{6.33})} = \frac{2.5}{2.797} \approx 0.894
\]

\[
\text{score(chunk1)} = 0.47 \times 0.894 \times 2 \approx 0.84
\]

**chunk2**（dl=5，只命中"配置"）：

\[
\frac{2.5}{1 + 1.5 \times (0.25 + 0.75 \times \frac{5}{6.33})} = \frac{2.5}{2.263} \approx 1.105
\]

\[
\text{score(chunk2)} = 0.47 \times 1.105 \approx 0.52
\]

**chunk3**（dl=6，只命中"数据库"）：

\[
\frac{2.5}{1 + 1.5 \times (0.25 + 0.75 \times \frac{6}{6.33})} = \frac{2.5}{2.442} \approx 1.024
\]

\[
\text{score(chunk3)} = 0.47 \times 1.024 \approx 0.48
\]

### 3.4 第 3 步：排序

```
chunk1 (0.84) > chunk2 (0.52) > chunk3 (0.48)
```

- 两个词都命中的 chunk1 遥遥领先
- chunk2 只命中一个词，但因**短**（词密度高）压过了更长的 chunk3

这就是 BM25 的全部工作。

## 四、BM25 与向量检索的互补

| 场景 | 向量检索（语义） | BM25（字面精确） |
|---|---|---|
| 用户问"数据库连不上怎么办" | 能找到"连接池配置"相关 chunk（语义近） | 命中"连接"（字面） |
| 用户问"PostgreSQL 17 的 vacuum 参数" | 专有名词语义向量不敏感，容易丢 | "postgresql"、"vacuum" 精确命中，稳 |
| 用户问"配置 3888 端口" | 数字/版本号/编号是向量弱项 | 数字精确匹配，强项 |
| "配置"这类高频词 | 语义定位准 | IDF 低，不起作用（恰好也不抢排名） |

两条路互补：**向量抓"意思对但字不对"，BM25 抓"字对但意思飘"**——这是模块七（检索与后处理）采用混合检索的原因。

## 五、在 DocMind 的落地形态

- **索引侧**：`chunks` 表建 `USING bm25` 索引，jieba 分词，chunk 增删改自动维护倒排表，业务代码零改动
- **检索侧**：`paradedb.match('content', 问题)` 自动分词 → 查倒排 → Tantivy 算分 → `paradedb.score(id)` 返回分数 → 排序取 TopK
- **融合侧**：BM25 分数与 cosine 分数量纲不同不能相加，下一步用 RRF 只按名次合并，两路结果分别来自 `Context.KeywordResults` 与 `SearchResults`
