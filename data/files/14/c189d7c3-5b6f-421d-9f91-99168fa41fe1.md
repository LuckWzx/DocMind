# 项目复盘汇报 - 开发中的问题（优化版本）

## 一、同步 vs 异步方案对比

### 原方案（同步调用扣子）的问题

| 问题 | 影响 |
|------|------|
| 接口耗时过长（几分钟级） | 用户等待时间长，体验差 |
| 前端一直 loading | 用户不知道任务进度 |
| 请求超时风险大 | 可能导致任务失败 |
| 服务端被长请求拖住 | 影响其他请求处理 |
| 中间状态无法实时告诉前端 | 用户无法感知任务进度 |
| 服务重启后任务无法恢复 | 执行到一半的任务丢失 |

### 优化后（异步链路）

| 优化点 | 效果 |
|--------|------|
| 接口快速返回（毫秒级） | 用户体验提升，任务后台执行 |
| 前端实时看到状态变化 | 排队→生成中→成功/失败，全程可见 |
| 服务端不被长耗时任务阻塞 | 系统整体稳定性提升 |
| 支持任务补偿和恢复机制 | 失败任务可自动重试，服务重启后可恢复 |

## 二、状态同步方式对比

### 单通道方案（仅 WebSocket）的问题

| 问题 | 场景 |
|------|------|
| 断线后实时消息丢失 | 网络波动导致 WebSocket 断开 |
| 刷新页面后状态丢失 | 用户刷新浏览器 |
| 重连后无法恢复断线期间的状态变化 | 错过任务状态更新 |

### 三通道组合方案（推荐）

| 通道 | 职责 | 解决的问题 |
|------|------|------------|
| WebSocket | 实时推送 | 状态变化第一时间通知前端 |
| `/game/pending` | 当前态快照 | 断线重连、页面刷新后恢复当前状态 |
| `/game/status/events` | 事件补拉 | 补拉断线期间漏掉的状态变化 |

**关键设计思想：** 前端不能只信 WebSocket，需要多通道保障状态同步的可靠性。

## 三、Redis Stream 的定位对比

### 常见误区

| 误区 | 问题 |
|------|------|
| Redis 存所有状态和业务数据 | 边界模糊，问题难以定位 |
| Redis 当作状态真相 | 持久化和查询能力弱 |

### 正确分工（推荐）

| 组件 | 职责 | 优势 |
|------|------|------|
| Redis Stream | 任务调度通道 | 高频读写，快速入队/消费 |
| MySQL | 任务状态真相 | 持久化、可追溯、支持复杂查询 |

**为什么这样设计？**
- Redis 适合高频读写的调度场景
- MySQL 适合需要持久化和查询的业务数据
- 边界清晰，问题更容易定位

## 四、并行处理能力对比

### 任务级并行 vs 单任务内部并行

| 方案 | 实现方式 | 适用场景 |
|------|----------|----------|
| 单任务内部并行 | 一个多游戏任务拆成多线程同时生成不同片段 | 复杂任务内部并行 |
| **任务级并行（本方案）** | 多个游戏任务可以同时推进 | 多任务并发处理 |

### 并行能力来源

| 来源 | 作用 |
|------|------|
| Redis Stream 多消费者 | 多个 worker 并发消费任务 |
| 扣子异步工作流 | 任务提交后 worker 立即释放，不阻塞 |

### 效果示例

```
任务A → worker1 提交给扣子 → worker1 继续处理下一条
任务B → worker2 提交给扣子 → worker2 继续处理下一条
任务C → worker3 提交给扣子 → worker3 继续处理下一条
```

## 五、状态管理对比

### 复杂状态 vs 精简状态

| 方案 | 状态设计 | 优缺点 |
|------|----------|--------|
| 复杂状态 | queued, generating, processing, uploading, success, failed... | 状态多，边界模糊，补偿困难 |
| **精简状态（推荐）** | queued → generating → success/failed | 前后端都易理解，边界清晰，补偿收口容易 |

### 状态设计原则

| 原则 | 说明 |
|------|------|
| 前后端都容易理解 | 减少沟通成本 |
| 状态边界清晰 | 每个状态含义明确，不易混淆 |
| 补偿和恢复更容易收口 | 失败任务处理逻辑统一 |

## 六、补偿机制对比

### 无补偿机制

| 问题 | 后果 |
|------|------|
| 失败任务全靠人工重试 | 运维成本高，用户体验差 |
| 服务重启后任务丢失 | 数据不一致，任务无法恢复 |
| 断线后状态无法恢复 | 用户看到的状态与实际不符 |

### 多层补偿机制（推荐）

| 补偿类型 | 实现方式 | 解决的问题 |
|----------|----------|------------|
| pending 恢复 | `/game/pending` 接口 | 断线重连后恢复当前态 |
| 失败重试 | 任务重新入队 | 扣子执行失败后自动重试 |
| 超时恢复 | 定时任务检测 | 长时间未完成的任务自动处理 |
| 事件补拉 | `/game/status/events` | 补拉断线期间的状态变化 |

## 七、总结：为什么这套方案更适合上线

| 维度 | 原方案 | 优化后方案 |
|------|--------|------------|
| 接口响应 | 慢（分钟级） | 快（毫秒级） |
| 用户体验 | 差（一直 loading） | 好（实时状态更新） |
| 系统稳定性 | 差（易被长任务阻塞） | 好（异步解耦） |
| 可靠性 | 差（无补偿机制） | 好（多层补偿） |
| 扩展性 | 差（单任务处理） | 好（任务级并行） |
| 维护性 | 差（状态复杂） | 好（状态精简） |

---

## 八、关键设计决策

1. **为什么选择异步而非同步？**
   - 接口更轻，用户体验更好
   - 状态更透明，前端可实时感知
   - 服务更稳，不会被长任务拖住
   - 更容易补偿，支持多层恢复机制

2. **为什么 Redis Stream 不是状态真相？**
   - Redis 适合高频调度，不适合持久化
   - MySQL 适合业务数据，支持复杂查询
   - 边界清晰，问题更容易定位

3. **为什么前端不能只依赖 WebSocket？**
   - 断线后实时消息丢失
   - 刷新页面后状态丢失
   - 需要多通道保障状态同步可靠性

4. **为什么状态设计要精简？**
   - 前后端都容易理解
   - 状态边界清晰
   - 补偿和恢复更容易收口
