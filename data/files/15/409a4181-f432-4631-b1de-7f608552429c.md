# mysql优化

> **SQL → 索引 → 表设计 → 执行计划 → 锁与事务 → 架构 → 参数配置**

基本覆盖了互联网公司的所有 MySQL 优化场景。

------

# 一、SQL 优化（最重要）

很多时候数据库慢，并不是数据库的问题，而是 SQL 写得不好。

## 1）避免 SELECT *

错误：

```sql
SELECT * FROM user;
```

正确：

```sql
SELECT id,name,age FROM user;
```

原因：

- 减少网络传输
- 减少回表
- 覆盖索引可以直接返回

------

## 2）避免全表扫描

例如

```sql
SELECT * FROM user
WHERE name='Tom';
```

如果

```
name
```

没有索引

那么

```
type = ALL
```

整个表都会扫描。

InnoDB 数据存储在聚簇索引叶子节点。索引本质是 B + 树导航结构，可以快速定位满足条件的数据；当没有可用索引，数据库没有快速定位的路径，只能顺着聚簇索引叶子链表逐页逐行遍历校验 where 条件，这就是全表扫描。即使存在索引，如果索引失效或者优化器评估全表扫描代价更低，也会走全表扫描。

------

## 3）分页优化

很多人这样写：

```sql
SELECT *
FROM article
LIMIT 100000,20;
```

问题：

数据库需要扫描

```
100020
```

条记录。

优化：

### 方法一：记录上一页ID（游标分页）

```sql
SELECT *
FROM article
WHERE id>100000
LIMIT 20;
```

这是互联网最常见的方法。

------

### 方法二：子查询

```sql
SELECT *
FROM article
WHERE id IN(
    SELECT id
    FROM article
    LIMIT 100000,20
);
```

减少回表。

------

## 4）避免函数操作

例如

```sql
WHERE YEAR(create_time)=2025
```

索引失效。

应该写

```sql
WHERE create_time>='2025-01-01'
AND create_time<'2026-01-01'
```

------

## 5）避免隐式类型转换

例如

id 是 int

写成

```sql
WHERE id='100'
```

某些情况下会影响索引使用。

最好

```sql
WHERE id=100
```

------

## 6）避免 OR

例如

```sql
WHERE age=20
OR city='北京'
```

可能导致索引失效。

可以改

```sql
UNION ALL
```

------

## 7）避免 NOT

例如

```sql
WHERE age!=18
```

一般不能很好利用索引。

------

## 8）避免前导%

```sql
LIKE '%abc'
```

索引失效。

可以

```
LIKE 'abc%'
```

------

# 二、索引优化（面试重点）

索引优化占 MySQL 优化的大部分内容。

------

## 1）选择高区分度字段

例如

```
gender
```

只有男女。

区分度极低。

不适合单独建索引。

而

```
phone
```

几乎唯一。

非常适合。

------

## 2）联合索引

例如

```sql
(name,age,city)
```

查询

```sql
WHERE name=?
AND age=?
```

可以命中。

查询

```sql
WHERE age=?
```

不能。

因为：

> 最左前缀原则

------

## 3）覆盖索引

例如

```sql
INDEX(name,age)
```

查询

```sql
SELECT name,age
FROM user
WHERE name='Tom';
```

不用回表。

速度最快。

------

## 4）减少回表

例如

```sql
SELECT *
```

一定要回表。

如果

```sql
SELECT id,name
```

覆盖索引即可。

------

## 5）索引不要太多

索引不是越多越好。

每次

```
INSERT
UPDATE
DELETE
```

都要维护索引。

------

## 6）索引长度

例如

VARCHAR(255)

如果前面几十位已经足够区分。

可以

```
前缀索引
```

例如

```sql
INDEX(name(20))
```

------

## 7）避免重复索引

例如

已经有

```sql
(name,age)
```

一般不需要

```sql
(name)
```

------

# 四、表设计优化

## 1）字段尽量小

例如

```
INT
```

不要用

```
BIGINT
```

如果业务够用。

------

## 2）避免 NULL

NULL 判断更复杂。

可以

```
NOT NULL
DEFAULT ''
```

------

## 3）选择合适数据类型

金额：

```
DECIMAL
```

不要

```
FLOAT
```

------

时间：

```
DATETIME
```

或

```
TIMESTAMP
```

------

## 4）范式与反范式

互联网一般：

适当冗余字段。

例如

订单保存：

```
商品名称
```

而不是每次 JOIN。

------

# 五、JOIN 优化

## 小表驱动大表

例如

```
100条
JOIN
1000万条
```

先扫描小表。

------

## JOIN 字段必须索引

例如

```sql
ON user.id=order.user_id
```

两个字段都最好有索引。

------

## 尽量避免多表 JOIN

超过

```
3~5
```

张表以后。

很多互联网公司开始拆 SQL。

------

# 六、排序优化

例如

```sql
ORDER BY create_time
```

如果

```
create_time
```

有索引。

无需 filesort。

------

联合索引：

```
(name,age)
```

排序：

```sql
ORDER BY name,age
```

效率最高。

------

# 七、事务优化

事务越短越好。

不要

```sql

COMMIT
```

容易锁住别人。

------

# 八、锁优化

避免：

# 十一、互联网项目常用优化套路（实战）

| 场景       | 常用优化方案                       |
| ---------- | ---------------------------------- |
| 查询慢     | 建索引 + EXPLAIN + SQL 改写        |
| 深分页     | 游标分页（Keyset Pagination）      |
| 高频读     | Redis 缓存                         |
| 大表       | 分库分表                           |
| JOIN 太多  | 适度反范式、拆分查询               |
| 排序慢     | 排序字段建索引，避免 `filesort`    |
| 写入慢     | 减少索引、批量插入、异步写入       |
| 锁竞争     | 缩短事务、降低锁粒度、热点数据缓存 |
| 数据量增长 | 归档历史数据、冷热分离             |
| 高并发     | 读写分离 + 缓存 + 分片             |

## 面试建议

如果面试的是后端开发岗位，建议把 MySQL 优化重点放在以下内容，覆盖率最高：

1. **索引优化**：B+Tree 原理、联合索引、最左前缀原则、覆盖索引、索引失效场景、回表。
2. **SQL 优化**：避免 `SELECT *`、深分页优化、`JOIN` 优化、`LIKE`、`OR`、函数和隐式类型转换导致的索引失效。
3. **执行计划分析**：熟悉 `EXPLAIN`，重点关注 `type`、`key`、`rows`、`Extra`。
4. **锁与事务**：理解 MVCC、行锁与间隙锁、事务隔离级别、死锁分析与长事务优化。
5. **高并发架构**：Redis 缓存、读写分离、分库分表、冷热数据分离等方案及适用场景。

掌握这几个方面，基本可以覆盖绝大多数中高级 Java/Go 后端岗位关于 MySQL 优化的考察内容。



## 2.小表驱动大表

小表驱动大表，小表数量小，使用其索引和条件对大表进行数据筛选，减少计算量，提高查询效率

## 3.尽量 连接查询代替子查询

子查询需要执行两次数据库查询，一次外部查询，一次嵌套子查询，使用连接查询减少数据库查询的次数，提高查询效率

连接查询，更好的利用数据库索引，

## 5.多条数据库数据插入时，尽量批量插入

一次insert代表一次connection耗费性能

## 6.limit如果过大尽量避免使用

传统分页代替，游标分页

7.尽量使用索引
